# SecureDocs 보안 개선 결과 보고서

> SecureDocs의 보안 결함을 코드에서 직접 수정하고, 공격을 다시 재현해 차단 여부를 확인한 결과입니다.
> 1차로 초기 취약점 23건(V-01 ~ V-23)을, 이어서 재검증·운영 점검에서 찾은 10건(R-01 ~ R-10)을 조치했습니다.
> 원본 코드 기준 진단은 [최초 취약점 분석](./SecureDocs-최초-취약점-분석.md)에, 항목별 원인과 수정 코드는 [보안 취약점 개선 내역](./SecureDocs-보안취약점-개선내역.md)에 있습니다.

| 항목 | 내용 |
|---|---|
| 작성일 | 2026-09-21 |
| 대상 | `app/` (Flask API), `static/` (프론트엔드), 설정·스키마·의존성·컨테이너 |
| 검증 방법 | pytest 회귀 테스트(`tests/`) — 테스트마다 임시 DB를 새로 시드하고 Flask 테스트 클라이언트로 공격 재현<br>운영 형태 컨테이너(gunicorn·비루트) 실행 후 HTTP 확인, 브라우저에서 CSP 위반 여부 확인, `pip-audit` 의존성 스캔 |

## 1. 요약

| 지표 | 결과 |
|---|---|
| 조치한 취약점 | **33건** — 1차 23건(Critical 7 · High 11 · Medium 5) + 후속 10건(High 4 · Medium 3 · Low 3) |
| 회귀 테스트 | **85개 중 85개 통과** |
| 의존성 취약점 | **0건** (`pip-audit`, 조치 전 20건) |
| 기존 기능 | 로그인 · 문서 CRUD · 공유 · 댓글 · 첨부 · JSON 백업 · PDF 내보내기 · 관리자 기능 정상 |
| 남은 과제 | 코드 결함 없음. 운영 인프라 선택 사항만 남음 (4장) |

**결론:** 확인된 취약점은 모두 조치했고, 공격 사슬(경로 조작 → 시크릿 유출 → 토큰 위조 → 관리자 장악)도 끊겼습니다.
토큰 폐기, 엄격한 CSP, CSRF 방어, 의존성 스캔까지 적용해 **한 겹의 방어가 뚫려도 다음 겹이 막는 구조**가 됐습니다.
운영 환경에 올릴 때는 5장의 체크리스트(데모 데이터 제거, 시크릿 주입 등)만 처리하면 됩니다.

| ID | 항목 | 위험도 | 조치 | 상태 |
|---|---|---|---|---|

| R-04 | JWT 폐기 수단 없음 | Medium | `jti` 폐기 목록 + 사용자별 토큰 세대 | ✅ |

| R-06 | CSRF 방어가 `SameSite`에만 의존 | Low | 쿠키 인증 요청에 커스텀 헤더 요구 | ✅ |
| R-07 | SSRF DNS 리바인딩 | Low | 검증한 IP로 직접 연결 | ✅ |

| R-09 | Docker 이미지에 시크릿·DB 포함 | High | `.dockerignore`, 빌드 시 시드 제거 | ✅ |
| R-10 | 개발 서버 · root 권한 실행 | Medium | gunicorn, 비루트, 프록시·레이트리밋 저장소 설정 | ✅ |

> **R-02를 "완화"로 둔 이유:** 아이디로 가입하는 구조에서는 "이미 쓰는 아이디"라는 사실을 완전히 숨길 수 없습니다. 완전히 없애려면 이메일 인증 기반 가입으로 바꿔야 합니다.

기능 결함도 함께 고쳤습니다.
- **PDF 내보내기:** 원본 파일을 만들지 않아 항상 실패하던 문제를 고쳐, 이제 PDF를 반환합니다.
- **비밀번호 재설정:** 토큰으로 새 비밀번호를 설정하는 단계(`/api/profile/reset-confirm`)를 추가했습니다.
- **`/api/auth/refresh`:** 임의 값을 돌려주던 스텁을 실제 토큰 교체로 바꿨습니다.

## 4. 남은 과제 (운영 인프라)

코드 수준의 알려진 결함은 없습니다. 아래는 배포 규모와 인프라에 따라 선택할 사항입니다.

| 영역 | 현재 | 권장 |
|---|---|---|
| 레이트리밋 저장소 | 기본값은 메모리(워커별 카운터) | 워커·서버가 여럿이면 `RATELIMIT_STORAGE_URI`로 Redis 지정 (`pip install redis`) |
| 시크릿 관리 | 환경변수 또는 볼륨의 `instance/secret.key` | KMS · Vault에서 주입, 주기적 교체 |
| 토큰 서명 | HS256 (대칭키) | 토큰을 검증하는 서비스가 늘어나면 RS256 · EdDSA |
| 데이터베이스 | SQLite | 동시 사용자가 많으면 PostgreSQL 등 |
| 재설정 토큰 전달 | `deliver_reset_token`이 로그만 남김 | 이메일 · SMS 발송 연동 |
| PDF 변환기 | 이미지에 LibreOffice 미포함 → 내보내기 `503` | 필요하면 `libreoffice-writer` 설치(이미지 크기 증가) 또는 별도 변환 서비스 |
| 회원가입 | 아이디 기반 (R-02 완화) | 이메일 인증 기반 가입 |

## 5. 운영 배포 체크리스트

코드는 운영 형태로 준비됐지만, **로컬 확인용 설정은 공개 환경에 그대로 가져가면 안 됩니다.**

- [ ] **데모 데이터 끄기** — `SEED_DEMO_DATA`를 설정하지 않기 (`docker-compose.yml`은 로컬용으로 `1`). 데모 계정의 비밀번호(`admin/admin123` 등)는 공개돼 있습니다.
- [ ] **시크릿 주입** — `JWT_SECRET`, `SECRET_KEY`, `DATA_KEY`를 환경변수로 전달 (`DATA_KEY`는 Fernet 키: `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`)
- [ ] **HTTPS와 프록시** — TLS를 종료하는 리버스 프록시 뒤에 두고 `TRUST_PROXY_HOPS=1`(프록시 수) 설정
- [ ] **자가채점 기능 제거** — `/flags`, `/api/flags/*` (`app/flags.py`, `static/flags.html`, `static/flags.js`)
- [ ] **이전 이미지 폐기** — R-09 수정 전에 빌드한 이미지를 공유한 적이 있다면 폐기하고 시크릿 교체

## 6. 재현 방법

```bash
# 로컬 확인 (데모 데이터 포함)
docker compose up --build        # http://localhost:5000

# 데모 데이터로 되돌리기
docker compose exec securedocs python -m app.seed
```

- 컨테이너는 비루트 사용자로 gunicorn을 실행하며, DB·업로드·시크릿은 `securedocs-data` 볼륨에 보존됩니다.
- 시크릿은 첫 기동 시 볼륨 안의 `instance/secret.key`에 생성됩니다(환경변수를 주면 그 값을 사용).
- 기존 DB는 기동 시 새 컬럼·테이블이 자동으로 추가됩니다. 이전 형식의 토큰은 거부되므로 한 번 다시 로그인하세요.
- `/flags` 자가채점 페이지는 남아 있지만, 플래그를 얻던 경로가 모두 막혀 **15개 중 어느 것도 더 이상 획득할 수 없습니다.**
