## 2. 관통하는 근본 원인

개별 결함은 달라 보이지만, 원인을 모으면 여섯 가지 패턴으로 정리됩니다. 이 여섯 가지가 곧 **시큐어코딩에서 먼저 고려해야 할 축**입니다.

| 패턴 | 이 앱에서 나타난 모습 | 시큐어코딩 원칙 |
|---|---|---|
| **블랙리스트로 방어** | SQL 키워드 제거(2-A), `<script>` 제거(2-C), 확장자 차단(3-B), `/`로 시작하는 경로만 차단(3-A) | 막을 것을 다 열거할 수 없다 → **허용목록**과 **구조적 분리** |
| **입력을 코드로 취급** | SQL 문자열 결합(2-A), 템플릿 소스에 결합(2-B), `innerHTML`(2-C), `pickle.loads`(7-A), `shell=True`(4장) | 입력은 끝까지 **데이터** — 바인딩, 값 주입, 출력 인코딩, 데이터 전용 포맷 |
| **인증과 인가를 혼동** | 로그인만 하면 남의 문서 조회·수정(5-A·5-B), 누구나 파일 다운로드(3-A) | 매 요청 **객체 단위 권한**을 확인 |
| **클라이언트의 주장을 신뢰** | 토큰 헤더의 `alg`(0), 토큰의 `role`(4-B), `remote_addr`(7-B), 요청의 `owner_id`(5-B) | 권한·알고리즘·신원은 **서버가 결정** |
| **시크릿·암호를 직접 관리** | 소스에 박힌 `JWT_SECRET`·`DATA_KEY`(0·3-A), 자체 XOR 암호(6-A), 빠른 무솔트 해시(0) | 시크릿은 **코드 밖**, 암호는 **검증된 라이브러리** |
| **필요 이상 노출** | 프로필에 해시·토큰·평문 주민번호(6-B), 실패 사유 구분(4-A), 트레이스백(4장), 로그의 비밀번호(0) | 응답·로그·오류는 **최소한만** |

## 3. 교시별 분석

### 0. 사전 준비 — 인증 설계

로그인해 쿠키를 받는 준비 단계처럼 보이지만, 이후 공격 대부분의 토대가 되는 **인증 설계 결함**이 이미 여기 모여 있었습니다.

**(1) JWT `alg=none` / 알고리즘 혼동 — 가장 치명적**

```python
# app/utils.py · decode_jwt (원본)
header = jwt.get_unverified_header(token)      # 공격자가 만든 헤더를 그대로 신뢰
alg = header.get("alg", "HS256")
if alg == "none":
    return jwt.decode(token, options={"verify_signature": False}, algorithms=["none"])
return jwt.decode(token, current_app.config["JWT_SECRET"], algorithms=[alg])

# app/config.py (원본)
JWT_ALGORITHMS = ["HS256", "none"]
```

- 토큰이 **스스로 주장하는 알고리즘**으로 검증했습니다. 알고리즘을 `none`으로 지정하면 서명 검증을 통째로 건너뛰므로, 키를 몰라도 관리자 권한 클레임을 담은 위조 토큰이 통과합니다.
- **고려했어야 할 것:** 허용 알고리즘은 서버가 고정(`["HS256"]`)하고, 토큰 헤더의 `alg`는 믿지 않는다. `none`은 금지. → **V-08**

**(2) 추측 가능한 서명 시크릿**

```python
# app/config.py (원본)
JWT_SECRET = "s3cr3t"
SECRET_KEY = ...          # 하드코딩
DATA_KEY = "..."          # 개인정보 암호화 키도 하드코딩
```

- HS256은 대칭키라 **검증 키가 곧 위조 키**입니다. 사전 단어 수준의 키는 오프라인 대입으로 금방 복구되고, 소스가 한 번 새면(3-A) 그대로 노출됩니다.
- **고려했어야 할 것:** 충분히 긴 난수 키를 환경변수·시크릿 매니저로 주입하고, 코드와 설정 파일에 두지 않는다. → **V-09**

**(3) 쿠키 `HttpOnly` 미설정**

```python
# app/auth.py · _auth_response (원본)
resp.set_cookie("token", token, httponly=False)
```

- 스크립트가 `document.cookie`로 토큰을 읽을 수 있어, 저장형 XSS(2-C) 하나로 **세션을 탈취**할 수 있었습니다. `Secure`·`SameSite`도 없었습니다.
- **고려했어야 할 것:** 인증 쿠키는 `HttpOnly` · `Secure` · `SameSite`. → **V-13**

**(4) 빠른 무솔트 해시**

```python
# app/utils.py · hash_password (원본)
return hashlib.sha256(password.encode()).hexdigest()   # 솔트 없음, 1회
```

- SHA-256은 **빠른** 해시라 GPU로 대량 시도가 가능하고, 솔트가 없어 같은 비밀번호는 같은 해시가 됩니다(레인보우 테이블). 주석의 "MD5 → SHA-256 상향"은 실질적인 개선이 아니었습니다.
- **고려했어야 할 것:** argon2·bcrypt·scrypt 같은 **느린 KDF** + 사용자별 솔트. → **V-12**

**(5) 민감정보 평문 로깅**

```python
# app/auth.py (원본)
log.info("신규 가입: username=%s password=%s", username, password)
log.info("로그인 성공: %s (token=%s)", username, user["api_token"])
```

- 로그 파일만 새어도 자격 증명과 API 토큰이 통째로 유출됩니다. 로그는 접근 통제가 느슨하고 백업·수집 시스템으로 복제되기 쉽습니다.
- **고려했어야 할 것:** 비밀번호·토큰·개인정보는 로그에 남기지 않는다(마스킹). → **V-20**

**(6) 예측 가능한 토큰 · 상수 시간이 아닌 비교 · 디버그 모드**

- `generate_token()`이 `random`(메르센 트위스터) 기반이라 **예측 가능**했고, API 토큰과 비밀번호 재설정 토큰이 모두 이 함수를 썼습니다.
- `tokens_match(a, b)`가 `a == b`로 비교해 **타이밍 공격**에 노출됐습니다.
- `DEBUG=True`로 실행해 오류 시 내부 정보가 노출될 수 있었습니다.
- **고려했어야 할 것:** 보안 난수는 `secrets`, 비교는 `hmac.compare_digest`, 운영은 `DEBUG=False`. → **V-22** (예측 가능한 토큰 처리는 비밀번호 재설정 토큰과 함께 **V-14** — [4장](#4-워크북-밖에서-함께-확인된-결함) 참조)

### 2교시 · 인젝션

#### 2-A. 검색 SQL 인젝션

```python
# app/documents.py · search_documents (원본)
safe = sanitize_search(keyword)
sql = f"SELECT id, owner_id, title, body, visibility FROM documents WHERE title LIKE '%{safe}%'"
rows = query_raw(sql)                                # 문자열을 그대로 실행

# app/utils.py · sanitize_search (원본)
for bad in current_app.config["SQL_BLACKLIST"]:      # 소문자 키워드 목록
    cleaned = cleaned.replace(bad, "")               # 대소문자 구분, 한 번만 치환
```

**무엇을 막고 무엇을 놓쳤나**
- 소문자 키워드 문자열만 지웠고, 정작 위험의 본질인 **"입력을 SQL 문자열에 이어 붙이는 방식"**은 그대로였습니다. 따옴표 하나로 `LIKE` 문자열을 닫고 절을 덧붙일 수 있습니다.
- `str.replace`는 대소문자를 구분하므로 대문자 키워드는 그대로 통과하고, 한 번만 치환하므로 키워드를 겹쳐 쓰는 방식으로도 우회됩니다 — **블랙리스트의 구조적 한계**입니다.
- 목록 API는 `owner_id`·`visibility` 필터가 있었지만 검색에는 그 조건이 없어, 임의 `SELECT`를 붙이면 **비공개 문서까지 노출**됐습니다.

**고려했어야 할 것**
- **파라미터 바인딩**으로 입력을 값으로만 넘긴다 — 같은 파일의 다른 함수는 이미 `?` 플레이스홀더를 쓰고 있었습니다.
- 블랙리스트(`sanitize_search`)는 폐기한다. 방어는 "위험 문자 제거"가 아니라 **데이터와 코드 분리**로 한다.
- 검색 결과에도 **권한 필터**를 적용한다. → **V-01**

#### 2-B. 서버 측 템플릿 인젝션(SSTI)

```python
# app/documents.py · render_document (원본)
template = header + "\n{{ body }}\n" + footer        # 사용자 입력이 '템플릿 소스'가 됨
html = render_template_string(template, body=doc["body"], title=doc["title"])
```

**진단**
- `header`/`footer`가 템플릿 **소스로 결합**됩니다. 즉 사용자 입력이 데이터가 아니라 **실행되는 코드(템플릿)**로 다뤄집니다. 산술식을 넣으면 계산된 값이 나오는 것이 그 증거입니다.
- Jinja2 표현식으로 Flask 설정 객체를 렌더링하면 서버 시크릿이 유출되고, 객체 그래프 탐색으로 **원격 코드 실행(RCE)**까지 확장될 수 있어 심각도가 매우 높습니다.

**고려했어야 할 것**
- 템플릿 구조는 서버가 고정하고, 사용자 입력은 **변수 값**으로만 전달한다(자동 이스케이프 동반).
- 정말 서식이 필요하면 Jinja2 전체가 아니라 제한된 마크업(허용목록)이나 샌드박스 환경을 쓴다. 근본적으로 **사용자 입력을 템플릿 컴파일에 넣지 않는다.** → **V-02**

#### 2-C. 저장형 XSS(댓글)

```python
# app/comments.py · add_comment (원본)
cleaned = re.sub(r"<script.*?>.*?</script>", "", body, flags=re.IGNORECASE | re.DOTALL)

# static/app.js (원본)
box.innerHTML = r.data.map(c => `... <div class="ct">${c.body}</div> ...`).join("");
```

**진단**
- 서버 필터는 `<script>` 쌍만 제거하는 블랙리스트라, 스크립트 태그 없이 이벤트 핸들러로 실행되는 입력(예: 이미지 로드 실패 핸들러)은 그대로 저장됐습니다. 이런 정규식은 태그 변형·중첩으로도 우회됩니다.
- 프론트가 댓글 본문을 `innerHTML`로 삽입해, 브라우저가 이를 **실제 DOM으로 파싱**하므로 핸들러가 실행됩니다. `textContent`였다면 문자열로만 표시됐을 것입니다.
- **저장형**이라 그 문서를 여는 모든 사용자(관리자 포함)에게 발동되고, `HttpOnly`가 없던 쿠키(0단계)와 결합하면 세션 탈취로 이어집니다.

**고려했어야 할 것**
- **출력 인코딩**이 핵심 — `innerHTML` 대신 `textContent`, 또는 프레임워크의 자동 이스케이프.
- 서버 정제는 정규식이 아니라 `bleach` 같은 검증된 라이브러리의 **허용목록** 방식.
- 심층 방어로 CSP(인라인 스크립트 금지)와 쿠키 `HttpOnly`. → **V-03**

### 3교시 · 파일 업로드·경로 조작

#### 3-A. 경로 조작 다운로드

```python
# app/files.py · download (원본)
name = request.args.get("name", "")
if name.startswith("/"):                                     # 절대경로만 차단
    return jsonify(error="잘못된 파일명입니다."), 400
path = os.path.join(current_app.config["UPLOAD_FOLDER"], name)   # '../' 그대로 결합
return send_file(path, as_attachment=True)
```

**진단**
- 검사가 "`/`로 시작하는가" 하나뿐이라, 상위 폴더로 올라가는 상대 경로는 전혀 걸러지지 않았습니다. `os.path.join`이 그 경로 요소를 그대로 이어 붙여 업로드 폴더 밖으로 빠져나갑니다.
- 업로드 쪽은 그나마 `safe_filename`을 썼지만 다운로드는 **정화 자체가 없었습니다.** 로그인만 하면 첨부 소유자 확인 없이 누구나 호출할 수 있었습니다.
- 이 결함으로 `config.py`가 유출되어 **`JWT_SECRET`·`DATA_KEY`가 노출**됐고, 이는 4교시·6교시·8교시 공격의 재료가 됐습니다.

**무엇을 검증했어야 하나**
- 파일명 문자열을 눈으로 훑는 것이 아니라, 경로를 **정규화한 뒤 허용 디렉터리 안에 있는지** 확인했어야 합니다.

```python
# 개선 방향
base = os.path.realpath(current_app.config["UPLOAD_FOLDER"])
target = os.path.realpath(os.path.join(base, name))
if os.path.commonpath([base, target]) != base:
    return jsonify(error="잘못된 파일명입니다."), 400
```

- 더 근본적으로는 파일명을 직접 받지 말고 **첨부 ID로 조회**하고, 그 첨부의 접근 권한을 함께 검사한다. → **V-06**

#### 3-B. 업로드 확장자 우회

```python
# app/utils.py · is_allowed_file (원본)
for ext in current_app.config["BLOCKED_EXTENSIONS"]:        # [".py", ".php", ".exe", ".sh"]
    if filename.lower().endswith(ext):
        return False
return True
```

**진단**
- 차단 목록에 없는 실행 가능 확장자는 그대로 통과합니다. 무엇이 "실행"되는지는 앱이 아니라 **웹서버 설정**이 정하므로, 앱이 위험 확장자를 전부 나열하는 것은 불가능합니다(열거의 불완전성).
- 다중 확장자·트레일링 문자·대소문자 등 변형도 우회 통로입니다.
- 특히 이 앱은 업로드물을 **같은 오리진의 정적 경로(`/static/uploads/`)에서 그대로 서빙**했습니다. `.html`·`.svg`를 올리면 브라우저에서 실행되어 저장형 XSS로 이어집니다. 저장명도 예측 가능해 추측·덮어쓰기 위험이 있었습니다.

**고려했어야 할 것**
- 블랙리스트 → **허용목록**(꼭 필요한 확장자만).
- 확장자만 믿지 말고 실제 내용(매직바이트)을 검증하고, 이미지면 재인코딩.
- 업로드물은 **웹 루트 밖**에 저장하고 전용 핸들러로만, 항상 `Content-Disposition: attachment` + `nosniff`로 내려준다. 저장명은 **무작위화**. → **V-07 · R-01**

### 4교시 · 인증 (JWT)

#### 4-A. 계정 열거

```python
# app/auth.py · login (원본)
if user is None:
    return jsonify(error="존재하지 않는 아이디입니다."), 401     # 분기 1
if not verify_password(password, user["password_hash"]):
    return jsonify(error="비밀번호가 일치하지 않습니다."), 401     # 분기 2
```

**진단**
- 실패 사유가 **서로 다른 메시지**로 갈려, 공격자는 아이디만 넣어봐도 그 계정의 존재 여부를 확정할 수 있었습니다. 로그인 화면에 없는 내부 서비스 계정의 존재도 이렇게 드러납니다.
- 존재하지 않는 아이디는 해시 검증을 건너뛰어 **응답 시간도 달랐습니다**(타이밍 사이드채널). 회원가입의 중복 아이디 응답도 같은 열거 통로였습니다.

**고려했어야 할 것**
- 실패 사유와 무관하게 **동일한 메시지·상태 코드**.
- 아이디가 없어도 **더미 해시를 검증**해 응답 시간을 맞춘다.
- 로그인·가입·재설정에 **레이트리밋**. → **V-11 · R-02**

#### 4-B. JWT 위조(관리자 장악)

```python
# app/sharing.py · require_admin (원본)
def require_admin():
    ident = require_login()
    return ident.get("role") == "admin"      # 서버 DB 재확인 없음
```

**진단**
- HS256은 대칭키라 **서명 키를 알면 임의 페이로드에 유효한 서명**을 만들 수 있습니다. 키가 약했을 뿐 아니라 3-A로 통째로 유출됐고, `alg=none`(0단계)까지 허용돼 키가 없어도 위조가 가능했습니다.
- 관리자 판정이 **오직 토큰의 `role` 클레임**에만 의존해, 위조 토큰 하나로 관리자 API 전부가 열렸습니다.

**서버는 알고리즘·권한을 어떻게 다뤄야 하나**
- 허용 알고리즘을 서버가 강제하고 `none`을 금지한다(V-08).
- 강한 시크릿을 코드 밖에서 관리한다(V-09). 서비스 간 검증이면 비대칭(RS256/EdDSA)으로 전환한다.
- 관리 작업은 토큰의 `role`을 믿지 말고 **매 요청 DB의 현재 권한을 재확인**한다. → **V-10**

### 5교시 · 접근통제

#### 5-A. IDOR(남의 문서 열람)

```python
# app/documents.py · get_document (원본)
if not require_login():                                       # 인증만 확인
    return jsonify(error="로그인이 필요합니다."), 401
doc = query("SELECT * FROM documents WHERE id = ?", (doc_id,), one=True)  # id만으로 조회
return jsonify(..., body=doc["body"], ...)                    # 권한 검사 없이 반환
```

**진단**
- "로그인했는가(인증)"만 확인하고 "이 문서를 볼 권한이 있는가(인가)"는 확인하지 않았습니다. 문서 번호만 바꾸면 소유자·공개 여부와 무관하게 아무 문서나 반환됩니다 — 전형적인 **IDOR**입니다.
- 목록 API는 `owner_id`/`visibility` 필터가 있었는데 단건 조회는 빠져 있었습니다. "화면에서 안 보이게" 숨겼을 뿐 서버가 막지 않았습니다.

**고려했어야 할 것**
- 요청자가 **소유자·공개·공유** 중 하나일 때만 반환하는 객체 단위 인가.
- 쿼리 단계에서 권한 조건을 함께 걸어 권한 없는 행은 애초에 반환하지 않는다.
- 목록·검색·다운로드·댓글 등 **모든 경로에 같은 규칙**을 공통 헬퍼로 적용한다. → **V-15**

#### 5-B. Mass Assignment(소유권 탈취)

```python
# app/documents.py · update_document (원본)
columns = ["title", "body", "visibility", "owner_id"]         # owner_id 까지 수정 허용
for col in columns:
    if col in data:                                           # 요청에 있으면 그대로 반영
        sets.append(f"{col} = ?"); args.append(data[col])
```

**진단**
- 서버가 **클라이언트 요청 필드를 그대로 DB 컬럼에 매핑**했고, 그 목록에 `owner_id`가 들어 있어 소유권을 덮어쓸 수 있었습니다. 소유권 검사도 없어 IDOR과 겹쳤습니다.
- 실제 서비스라면 `role`·`is_admin`(권한 상승), `balance`(금액), `email_verified`(검증 우회), `password_hash`(계정 탈취) 같은 필드가 모두 위험합니다.

**고려했어야 할 것**
- 수정 가능한 필드를 **명시적 허용목록**으로 제한한다. `owner_id`처럼 서버가 통제할 필드는 입력에서 받지 않는다.
- 수정 전에 소유권/권한을 확인하고, `visibility` 같은 값은 열거값만 허용하는 **스키마 검증**을 붙인다.
- 소유권 이전이 정말 필요하면 별도의 인가된 엔드포인트로 분리한다. → **V-16**

#### 5-C. 권한 검사 fail-open · 공유 소유권 미검사 (워크북 밖 · 함께 확인)

```python
# app/sharing.py · can_access (원본)
    except Exception as e:
        log.warning("권한 확인 중 오류: %s", e)
        return True                      # 오류 시 '허용' — fail-open

# app/sharing.py · share_document (원본): 소유권 확인 없이 shares 에 INSERT
```

**진단**
- `can_access`가 예외 시 `True`(허용)를 반환하는 **fail-open** 구조였습니다. 원본에서는 이 헬퍼가 실제 호출되지 않는 잠재 결함이었지만, 하드닝으로 인가 검사(5-A)에 연결하면서 반드시 **fail-closed**로 바로잡아야 하는 지점입니다.
- 실제로 활성화돼 있던 결함은 `share_document`의 **소유권 미검사**로, 누구나 남의 문서를 임의 사용자에게 공유할 수 있었습니다.

**고려했어야 할 것**
- 권한 판단은 오류 시 **거부(fail-closed)**가 기본값이어야 한다.
- 공유·수정 등 상태를 바꾸는 작업은 **소유자(또는 명시적 위임)**만 허용한다. → **V-17**

### 6교시 · 암호화·민감정보

#### 6-A. 개인정보 복호화 체인

```python
# app/utils.py (원본) — 자체 '암호화'
out = "".join(chr(ord(c) ^ ord(key[i % len(key)])) for i, c in enumerate(plain))  # 반복키 XOR
return base64.b64encode(out.encode("utf-8", "surrogatepass")).decode()            # Base64
```

**진단**
- **반복 키 XOR**은 고전적으로 깨지는 방식입니다. 짧은 키가 반복되어 패턴이 생기고, 형식이 정해진 데이터(주민번호)와 결합하면 키를 복원할 수 있으며, 무결성·인증이 전혀 없습니다.
- 키가 소스에 **하드코딩**되어, 소스가 한 번 새면(3-A) 저장된 데이터가 한꺼번에 복호화됩니다.
- **Base64는 암호화가 아니라 인코딩**입니다 — 비밀이 없어 누구나 되돌릴 수 있습니다.
- 이 값은 2-A(SQLi)로 덤프되고 3-A로 키가 유출되어 복호화까지 이어지는 **연쇄 공격**의 종착점이었습니다.

**고려했어야 할 것**
- 자체 암호 폐기, 검증된 **인증 암호(AEAD, 예: Fernet·AES-GCM)** 사용.
- 키를 코드에서 분리(환경변수·KMS·Vault), 로테이션·접근통제.
- 주민번호 등은 **최소 수집**, 표시용이면 마스킹, 대조용이면 솔트 해시. → **V-18**

#### 6-B. 민감정보 응답 노출

```python
# app/profile.py · get_profile (원본)
return jsonify(..., ssn=decrypt_field(u["ssn_enc"]),          # 복호화된 평문 주민번호
               api_token=u["api_token"], password_hash=u["password_hash"])
```

**진단**
- 화면에 불필요한 민감 필드까지 전부 내려줬습니다 — 재사용 가능한 **API 토큰**, **비밀번호 해시**, **평문 주민번호**. 클라이언트가 쓰지 않아도 응답에 실리는 순간 유출입니다(과다 노출).
- 4-B 위조 토큰으로 관리자 프로필을 조회하면 관리자 API 토큰까지 노출됐습니다.

**고려했어야 할 것**
- 응답을 **화이트리스트(DTO)**로 직렬화하고, `password_hash`·`api_token`은 어떤 프로필 응답에서도 반환하지 않는다.
- 주민번호는 마스킹, API 토큰은 재발급 시 한 번만 표시. → **V-19**

### 7교시 · 예외·로그·역직렬화·SSRF

#### 7-A. 역직렬화 RCE

```python
# app/tools.py · import_backup (원본)
if fmt == "yaml":
    restored = yaml.load(blob, Loader=yaml.Loader)     # 안전하지 않은 로더
else:
    restored = pickle.loads(base64.b64decode(blob))    # 임의 객체 역직렬화
```

**진단**
- `pickle`은 단순 데이터 포맷이 아니라 **객체를 재구성하는 과정에서 코드를 실행**합니다. 역직렬화 시 객체가 지정한 호출을 그대로 수행하므로, 공격자가 만든 데이터를 복원하면 임의 명령이 실행됩니다(RCE). `yaml.load(Loader=yaml.Loader)`도 같은 위험입니다.
- 즉 **"복원"이 곧 "실행"**이며, 신뢰할 수 없는 입력을 역직렬화하는 것 자체가 코드 실행 통로입니다.

**고려했어야 할 것**
- 신뢰할 수 없는 입력에는 `pickle`·`yaml.Loader`를 쓰지 않는다. **JSON**처럼 코드 실행이 없는 데이터 포맷 + 스키마 검증, YAML이 필요하면 `safe_load`.
- 심층 방어로 최소 권한 실행(비루트)·컨테이너 격리. → **V-05**

#### 7-B. SSRF

```python
# app/tools.py (원본)
r = requests.get(url, timeout=5)                         # 사용자가 준 URL을 서버가 그대로 요청
...
if request.remote_addr not in ("127.0.0.1", "::1"):     # 내부 API를 '출처 IP'로만 통제
    return jsonify(error="내부에서만 접근 가능합니다."), 403
```

**진단**
- 미리보기가 사용자가 준 URL을 **서버가 대신 요청**하므로, 그 요청의 출발지는 외부 공격자가 아니라 **서버 자신**이 됩니다. 내부 API는 출처가 loopback인지로만 통제해, 서버가 스스로에게 보낸 요청이 이 검사를 통과했습니다(confused deputy).
- 클라우드에서는 **메타데이터 서비스(`169.254.169.254`)**로 임시 자격 증명을 탈취하거나, 내부 관리 API·DB·다른 마이크로서비스가 표적이 됩니다.

**고려했어야 할 것**
- 대상 URL을 **허용목록**으로 제한하고, 사설·loopback·링크로컬 대역을 차단, `http`/`https`만 허용.
- DNS 재바인딩 방어(해석된 IP 검증, 리다이렉트 미추종).
- 접근통제를 **출처 IP에 의존하지 않고** 인증 토큰·mTLS·네트워크 정책으로 한다. → **V-21**

### 8교시 · 종합 체인

세 단계는 각각 앞 교시에서 본 결함이며, 이어 붙이면 **로그인만 한 일반 사용자 → 서버 관리자 완전 장악**이 됩니다.

```
① 경로 조작(3-A)  ─▶ config.py 유출 ─▶ JWT_SECRET 획득
② 유출 키로 토큰 위조(4-B / 0단계) ─▶ 관리자 role 클레임에 유효 서명
③ 관리자 판정이 role 클레임만 신뢰(4-B) ─▶ 관리자 API 장악
```

**왜 "중간 위험"이 모이면 "치명적"이 되나**
- 각 링크는 단독으로는 부분적입니다 — 경로 조작은 "파일 읽기", 약한 시크릿은 "언젠가 위험", `role` 신뢰는 "토큰이 진짜라면 정상".
- 그러나 **한 결함의 산출물이 다음 결함의 입력**이 됩니다. 파일 읽기 → 시크릿 → 유효 토큰 위조 → 권한 통과로 신뢰의 사슬이 한 바퀴 돌아 인증·인가 전체가 무의미해집니다. 실제 위험은 개별 항목이 아니라 **연결(compounding)**에서 나옵니다.
- 이 앱은 더 나아가 3-A로 `DATA_KEY`까지 유출 → 2-A로 암호문 덤프 → 6-A 복호화, 또는 7-A로 RCE까지 여러 완결 경로가 있었습니다.

**가장 먼저 고쳐야 할 것 — 두 관점**

| 관점 | 1순위 | 이유 |
|---|---|---|
| 체인 차단(즉효) | **경로 조작(3-A)** | 이 침해 경로의 입구. 막으면 ②③이 시작조차 못 한다 |
| 근본 원인(재발 방지) | **시크릿 분리 + 알고리즘/권한 설계** | 키가 유출돼도 위조 불가, 위조돼도 권한이 안 열리게 |

- 경로 조작만 고치면 이 체인은 막지만, 시크릿이 여전히 약하고 소스에 박혀 있으면 로그·백업·저장소 노출 등 다른 경로로 다시 샙니다.
- 그래서 **심층 방어**로 네 겹을 함께 세워야 합니다: ① 입구(경로 봉인) ② 비밀(시크릿 분리·강화) ③ 신뢰(알고리즘 고정) ④ 권한(서버가 매 요청 재확인). **네 겹 중 하나만 제대로 있었어도 이 체인은 끊깁니다.**

## 5. 시큐어코딩 체크리스트

이 앱의 실패를 뒤집으면, 코드를 쓰거나 리뷰할 때의 점검표가 됩니다.

- [ ] **입력은 데이터로 다뤘는가** — SQL은 파라미터 바인딩, 템플릿은 값 주입, 출력은 이스케이프, 역직렬화는 JSON, 명령은 인자 리스트(셸 미사용)
- [ ] **블랙리스트에 의존하지 않는가** — 확장자·필드·대상 호스트·알고리즘·역할 값은 허용목록
- [ ] **인증과 인가를 구분했는가** — 로그인 여부와 별개로, 객체마다 소유·공유·역할을 매 요청 확인
- [ ] **클라이언트 주장을 믿지 않는가** — 알고리즘·역할·신원·출처 IP는 서버가 결정
- [ ] **시크릿이 코드 밖에 있는가** — 하드코딩 금지, 환경변수·시크릿 매니저, 강한 난수, 로테이션
- [ ] **암호를 직접 만들지 않았는가** — 검증된 인증 암호(AEAD), 느린 비밀번호 해시(argon2 등), 보안 난수(`secrets`), 상수 시간 비교
- [ ] **필요 이상으로 노출하지 않는가** — 응답은 화이트리스트, 오류는 일반 메시지, 로그에 비밀 금지, 실패 사유 미구분
- [ ] **경로·파일을 정규화·봉인했는가** — `realpath` + 허용 디렉터리 확인, 업로드물은 웹 루트 밖 + `attachment`
- [ ] **한 겹이 뚫려도 다음 겹이 막는가** — 입구·비밀·신뢰·권한을 각각 방어(심층 방어)

> 각 항목을 실제로 어떻게 고쳤는지는 [개선 내역](./02-개선내역.md)에, 고친 뒤 공격이 막히는지 검증한 결과는 [결과 보고서](./03-결과보고서.md)에 있습니다.
