# SecureDocs 운영 문서

서버를 켜고·끄고·테스트하고·관리하는 **핵심 운영 명령**을 `scripts/` 스크립트로 정리했습니다. 이 문서는 각 스크립트의 용도·옵션·내부 동작·문제 대응을 설명합니다.

> 이 문서와 `scripts/`는 **로컬·데모 운영(Docker Compose)** 기준입니다. 실제 프로덕션 배포의 남은 과제(TLS·다중 워커·시크릿 관리 등)는 [3. 결과 보고서 §5](03-결과보고서.md#5-운영-배포에서-남는-작업)에 있습니다.

## 1. 사전 요구사항

| 도구 | 용도 | 확인 |
|---|---|---|
| Docker + Compose v2 이상 | 서버 기동·테스트·시드 (기본 실행 경로) | `docker compose version` |
| curl | 헬스체크 | 대부분 기본 설치 |
| Node.js 24+ | 프론트 보안 테스트 (`test.sh --frontend`) | `node --version` |
| openssl | 시크릿 생성 (`gen-secrets.sh`)·로컬 운영 회귀 테스트 | `openssl version` |
| Python 3.12 | 로컬 모드(`--local`) 실행·테스트 | `python3 --version` |

- 스크립트는 Bash가 필요하며 지원·검증 기준은 Linux/macOS입니다. Windows는 Linux 환경(예: WSL)에서 별도 확인해야 합니다.
- 모든 스크립트는 **어느 경로에서 실행해도** 저장소 루트를 기준으로 동작합니다(`scripts/lib.sh`가 루트로 이동).
- 제공된 Compose의 **호스트 공개 포트**와 로컬 개발 서버는 `127.0.0.1:5000`에 바인딩됩니다. 컨테이너 내부 gunicorn은 `0.0.0.0:5000`을 사용하므로 별도 Docker 실행·프록시·포트 설정의 노출 범위는 다시 확인해야 합니다.
- 공용 설정·헬퍼는 `scripts/lib.sh`에 있습니다(직접 실행용 아님). 각 스크립트는 `-h`/`--help`로 사용법을 봅니다.

## 2. 스크립트 한눈에

```bash
scripts/
├── lib.sh          # 공용 함수·설정 (source 전용)
├── start.sh        # 서버 기동 (Docker 백그라운드 + 헬스체크)
├── stop.sh         # 서버 종료 (--volumes 로 데이터까지 삭제)
├── restart.sh      # 재빌드·재기동 + 헬스체크
├── status.sh       # 컨테이너 상태 + 헬스 + 포트
├── logs.sh         # 로그 스트리밍
├── test.sh         # 회귀 테스트 + bandit + pip-audit + 프론트
├── scan.sh         # 정적 분석·의존성 감사 (+ 리포트)
├── seed.sh         # 데모 데이터로 DB 초기화 (파괴적)
├── cleanup.sh      # 실패한 파일 삭제 재시도
└── gen-secrets.sh  # 운영 시크릿(.env) 생성
```

| 목적 | 명령 |
|---|---|
| 처음 기동 | `scripts/start.sh` |
| 상태 확인 | `scripts/status.sh` |
| 로그 보기 | `scripts/logs.sh` |
| 코드 수정 반영 | `scripts/restart.sh` |
| 전체 검증 | `scripts/test.sh` |
| 종료 | `scripts/stop.sh` |
| 완전 초기화 | `scripts/stop.sh --volumes` |

## 3. 서버 생명주기

### 기동 — `start.sh`

```bash
scripts/start.sh              # 이미지 빌드 → 백그라운드 기동 → 헬스체크
scripts/start.sh --no-build   # 재빌드 없이 기동 (빠름)
scripts/start.sh --local      # 로컬 개발 서버(python run.py) 포그라운드 — 운영 금지
```

- Docker 모드: `docker compose up -d --build` 후 `http://127.0.0.1:5000/`가 응답할 때까지 최대 60초 대기합니다.
- 이미 실행 중이면 상태만 보여주고 끝냅니다.
- 기본은 `SEED_DEMO_DATA=1`이며 DB가 없는 첫 기동에만 데모 계정·문서가 들어갑니다. `.env`의 `SEED_DEMO_DATA=0`으로 끌 수 있고, `gen-secrets.sh`가 생성한 설정에는 `0`이 들어갑니다.
- `--local`은 개발용 Flask 서버라 운영에 쓰지 않습니다. `.venv`가 필요합니다(`test.sh --local`이 없을 때 만듭니다). 이 스크립트는 PATH의 `python3`를 사용하므로 먼저 Python 3.12인지 확인하거나 [README의 로컬 설치](../README.md#로컬-python-개발)대로 가상환경을 준비하세요.
- `--local` 서버는 실행한 터미널의 Ctrl+C로 종료합니다. `stop.sh`·`restart.sh`·`logs.sh`·`status.sh`·`seed.sh`·`cleanup.sh`는 Docker용이며 로컬 Python 프로세스를 관리하지 않습니다.

### 종료 — `stop.sh`

```bash
scripts/stop.sh               # 컨테이너만 종료 — DB·업로드·시크릿 볼륨 보존
scripts/stop.sh --volumes     # 데이터 볼륨까지 삭제 (되돌릴 수 없음, 확인 필요)
scripts/stop.sh --volumes --yes   # 확인 없이 완전 삭제
```

- 기본 종료는 데이터를 지우지 않습니다. 다음 `start.sh`에서 이전 데이터로 이어집니다.
- `--volumes`는 Compose의 `securedocs-data` 볼륨(DB·업로드·자동 생성 키)을 삭제합니다. 실제 볼륨 이름에는 보통 Compose 프로젝트 접두사가 붙습니다. 호스트 `.env`와 외부 시크릿 저장소는 삭제하지 않습니다. **시크릿 키가 사라지면 기존 암호문을 복호화할 수 없습니다.**

### 재기동 — `restart.sh`

```bash
scripts/restart.sh            # 변경된 코드/이미지를 재빌드하여 재생성 + 헬스체크
```

코드·환경변수 변경 후 반영할 때 사용합니다. 기존 DB가 있으면 `DATA_KEY`를 보존해야 합니다. 새 키로 바꾸는 것은 데이터 마이그레이션이 아니며, 기존 암호문은 복호화되지 않습니다.

`start.sh`·`restart.sh`의 헬스 대기는 기동 명령이 끝난 뒤부터 최대 60초입니다. 상태 검사에서 컨테이너 중지·HTTP 오류는 실패 종료 코드로 반환합니다.

홈(`/`)의 HTTP 성공 응답만 확인하므로 로그인·DB 쓰기·외부 연동까지 검사하는 readiness 검사는 아닙니다. 별도의 Docker `HEALTHCHECK`도 설정돼 있지 않습니다.

### 상태·로그 — `status.sh` / `logs.sh`

```bash
scripts/status.sh             # 컨테이너 상태 + 헬스(정상/무응답) + 포트
scripts/logs.sh               # 실시간 로그 (기본 최근 100줄부터, Ctrl+C 로 종료)
TAIL=500 scripts/logs.sh      # 최근 500줄부터
scripts/logs.sh --since 10m   # docker compose logs 인자 그대로 전달
# 실행 중인 서비스의 애플리케이션 로그는 별도 확인:
docker compose exec securedocs tail -n 100 /app/instance/app.log
```

`logs.sh`는 컨테이너 stdout/stderr(기동·gunicorn 접근 로그 등)를 보여줍니다. 앱은 `app/config.py`의 `LOG_FILE`(기본 `instance/app.log`)에 별도로 기록합니다. 키·토큰 값이 포함될 수 있는 환경변수 전체 출력으로 문제를 진단하지 마세요. 로그 회전·보존기간은 자동 구성돼 있지 않습니다.

## 4. 테스트·보안 검증

### 전체 검증 — `test.sh`

```bash
scripts/test.sh               # 회귀 테스트 + bandit + pip-audit + 프론트 (Docker, CI와 동일한 3.12)
scripts/test.sh --unit        # pytest 만
scripts/test.sh --scan        # bandit + pip-audit 만
scripts/test.sh --frontend    # 프론트(node) 만
scripts/test.sh --local       # Docker 대신 로컬 .venv 사용(없으면 자동 생성)
```

- 기본은 **Docker 컨테이너**에서 실행해 호스트 Python에 패키지를 설치하지 않고 CI와 같은 Python 3.12 계열을 씁니다. Docker 이미지·빌드 캐시는 호스트에 남습니다. OS·실행 사용자 등은 CI와 다를 수 있습니다. 원본은 읽기 전용으로 마운트하고 테스트에 필요한 소스만 사본에 복사하므로 실제 `instance/`는 수정하지 않습니다. 테스트 컨테이너는 개발 도구 설치를 위해 root로 실행되며 서비스의 비루트 실행과 구분됩니다.
- 프론트 테스트는 호스트의 `node`를 사용합니다. `node`가 없거나 테스트가 실패하면 전체 명령도 실패합니다. `--frontend`는 Docker·Python 설치 없이 실행할 수 있습니다. 모든 단계는 실패를 종료 코드에 반영합니다.
- 최근 검증 결과: **회귀 테스트 150개 통과 · 프론트 3개 통과 · bandit 0건 · pip-audit 0건.** 기준 시점·환경은 [검증 기록](security-review/verification.txt)에 있습니다. 의존성 감사 결과는 취약점 데이터베이스 갱신에 따라 달라질 수 있습니다.

### 정적 분석·의존성 감사 — `scan.sh`

```bash
scripts/scan.sh               # bandit -r app/ + pip-audit -r requirements.txt
scripts/scan.sh --report      # docs/security-review/ 에 bandit HTML·JSON + 의존성 JSON 갱신
```

- bandit 초기 10건은 모두 오탐/설계상 안전으로 분류해 근거를 단 `# nosec`로 억제돼 있습니다(자세히는 [3. 결과 보고서 §1](03-결과보고서.md#bandit-정적-분석--초기-10건-분류)).
- 스캔은 빌드된 이미지의 **일회용 테스트 컨테이너**에서 실행합니다. 런타임 서비스는 비루트이며 개발 도구가 없으므로 `compose exec ... pip install` 방식은 사용하지 않습니다. `--report`는 리포트 디렉터리만 쓰기 마운트하며, 보고서 생성·감사 중 하나라도 실패하면 실패 종료합니다. 의존성 JSON 원본도 함께 갱신됩니다.

## 5. 데이터 관리

### 데모 데이터로 초기화 — `seed.sh`

```bash
scripts/seed.sh               # 확인 후 재시드
scripts/seed.sh --yes         # 확인 없이 재시드
```

- **파괴적입니다.** 기존 사용자·문서·첨부·공유를 모두 지우고 데모 데이터(`admin/admin123` 등)로 되돌립니다.
- 실행 중인 서비스는 먼저 중지하고 임시 컨테이너에서 시드합니다. 성공한 경우에만 원래 실행 중이던 서비스를 재기동합니다. 실패 시 중지 상태를 유지하므로 로그와 데이터를 확인한 뒤 복구하세요.
- 재시드 전 JWT는 무효화됩니다. 이후 일반 회원 가입으로 같은 사용자 ID가 재사용되어도 이전 토큰을 수락하지 않습니다. 등록된 첨부는 삭제 큐로 옮겨 정리하고 기존 실패 큐도 보존합니다. 파일 삭제 실패 시 `cleanup.sh`로 재시도합니다. DB에 등록되지 않은 고아 파일·백업 파일은 자동 삭제 대상이 아닙니다.
- `python -m app.seed` 직접 실행도 파괴적입니다. 동시 요청이 없는 상태에서만 사용하세요.
- 운영 데이터를 이 명령으로 초기화하지 마세요. 업그레이드는 [3. 결과 보고서 §4](03-결과보고서.md#4-기존-데이터의-업그레이드)를 따릅니다.

### 파일 삭제 큐 정리 — `cleanup.sh`

```bash
scripts/cleanup.sh            # pending_file_deletions 큐의 실패한 파일 삭제를 재시도
```

문서 삭제·재시드 시 실제 파일 unlink가 실패하면 큐에 남습니다. 앱 시작 때 자동 재시도하지만, 주기적으로(예: cron) 이 명령을 돌려 남은 작업을 처리합니다. 명령 실행 성공만으로 삭제 완료를 판단하지 말고 출력의 `남은 삭제 작업: 0`과 로그를 확인하세요.

### 백업과 복구 범위

현재 전용 백업·복구 스크립트는 없습니다. `/api/tools/import`는 호출자 소유의 문서 하나를 생성하는 JSON 가져오기이며 사용자·권한·첨부·키를 복원하지 않습니다. 데이터 복구는 다음 범위를 갖춘 별도 절차가 필요합니다.

1. 쓰기 요청을 중단하고 서비스가 멈춘 상태에서 DB·업로드·삭제 큐를 포함한 데이터 볼륨을 같은 시점으로 백업합니다. `stop.sh --volumes`는 백업 명령이 아닙니다.
2. 자동 생성 키는 컨테이너의 `/app/instance/secret.key`(데이터 볼륨)에 있고, 환경변수 키는 호스트 `.env` 또는 외부 시크릿 저장소에 있습니다. 실제 사용 중인 키와 배포 설정·코드 버전을 함께 보존하고 백업 접근 권한을 제한합니다.
3. 원본과 분리된 복구 환경에서 DB·첨부·동일한 `DATA_KEY`를 복원합니다. 키 파일은 앱 사용자 소유·`0600`, 데이터 경로는 UID 10001이 읽고 쓸 수 있어야 합니다. 기존 사용자·첨부 접근·주민번호 복호화·삭제 큐를 확인한 뒤 서비스 복구 여부를 결정합니다.
4. 백업 시점 이후 폐기한 JWT 상태가 복원에서 되돌아갈 수 있습니다. 복구 후 기존 로그인을 허용할지 결정하고, 전체 무효화가 필요하면 JWT 서명 키를 교체해 재로그인시키세요. **암호화용 `DATA_KEY`는 그대로 보존**합니다.

보존기간·복구 목표·정기 복구 연습은 운영자가 정의해야 합니다. 위 절차의 실제 복구 시험은 이번 검증에 포함되지 않았습니다.

## 6. 시크릿·환경 변수

### 시크릿 생성 — `gen-secrets.sh`

```bash
scripts/gen-secrets.sh            # 신규 설치용 키 생성 + SEED_DEMO_DATA=0 (Git·이미지 제외)
scripts/gen-secrets.sh --print    # 파일에 쓰지 않고 화면에만 출력
scripts/gen-secrets.sh --force    # 기존 .env 전체 교체 (기존 데이터용 키 회전 아님)
```

- `JWT_SECRET`·`SECRET_KEY`는 `openssl rand -hex 32`(32바이트), `DATA_KEY`는 유효한 Fernet 키를 만듭니다.
- 생성된 `.env`와 임시 파일은 생성 시점부터 권한 `600`이며 Git·Docker 빌드에서 제외됩니다. **절대 커밋하지 마세요.**
- **신규 설치 전용입니다.** 기존 볼륨을 사용 중이면 기존 키를 보존해 설정하세요. `--force`는 `.env`의 사용자 설정까지 전체 교체하며, 기존 암호문의 재암호화나 키 회전을 수행하지 않습니다. `--print` 출력도 시크릿이므로 로그·화면 공유에 남기지 마세요.
- 생성된 설정은 `SEED_DEMO_DATA=0`입니다. 빈 DB로 시작하며 회원가입은 일반 사용자만 생성합니다. 운영용 최초 관리자 생성 절차는 별도로 마련해야 합니다.
- Compose가 `.env`를 읽고 YAML에 나열된 변수만 컨테이너에 전달합니다. 같은 이름의 셸 환경변수가 있으면 `.env`보다 우선하므로 기존 export 값도 확인하세요. 적용하려면 `scripts/restart.sh`.
- `python run.py`·`python -m app.seed`·`start.sh --local`은 `.env`를 자동 로드하지 않습니다. 필요한 값을 프로세스 환경에 별도로 주입해야 합니다. 임의의 `.env` 파일을 검증 없이 shell source하지 마세요.
- `.env`가 없으면(기본) 앱이 첫 기동 때 `instance/secret.key`에 키를 자동 생성합니다 — 로컬 데모는 별도 설정 없이 동작합니다.

> **로컬 HTTP 주의:** `COOKIE_SECURE=1`은 HTTPS 사용을 전제로 합니다. localhost/루프백 예외는 브라우저에 따라 달라 쿠키 인증이 실패할 수 있습니다. 로컬 HTTP 데모는 기본값 `0`, 운영 HTTPS는 `1`을 사용하세요.

### 환경 변수

`docker-compose.yml`은 아래 변수를 `.env`에서 주입하며, 없으면 로컬 데모용 기본값을 씁니다. 운영에 그대로 적용하지 마세요.

| 변수 | 기본값 | 설명 |
|---|---|---|
| `JWT_SECRET` / `SECRET_KEY` | (빈 값 → 자동 생성) | 32바이트 이상 |
| `DATA_KEY` | (빈 값 → 자동 생성) | Fernet 키 |
| `SEED_DEMO_DATA` | `1` | DB가 없을 때 데모 시드; 생성된 `.env`와 운영은 `0` |
| `COOKIE_SECURE` | `0` | `1`이면 Secure 쿠키 강제(HTTPS 전용) |
| `TRUST_PROXY_HOPS` | `0` | 앞단 리버스 프록시 수 |
| `RATELIMIT_STORAGE_URI` | `memory://` | 다중 워커면 Redis 등 공유 저장소 |
| `ENABLE_TRAINING_ROUTES` | `0` | 자가채점·예제 API 활성화(운영 금지) |

`CONVERTER_BIN`도 Compose에서 전달하며 기본값은 `/usr/bin/soffice`입니다. 기본 이미지에는 LibreOffice가 없어서 PDF 내보내기는 `503`을 반환합니다. `RATELIMIT_STORAGE_URI`에 Redis 주소만 적어도 Redis 서버나 Python 클라이언트가 설치되지는 않습니다. 서버와 클라이언트 의존성을 배포·이미지 빌드에 추가해야 합니다. 전체 설정은 `app/config.py`에 있으며, 환경변수로 읽지 않는 `Config` 상수는 코드/앱 설정으로 변경합니다.

## 7. 자주 쓰는 운영 시나리오

**처음 실행**
```bash
scripts/start.sh          # 빌드 → 기동 → 헬스체크
# 브라우저: http://127.0.0.1:5000  (admin/admin123)
```

**코드를 고친 뒤 반영**
```bash
scripts/test.sh           # 먼저 검증
scripts/restart.sh        # 재빌드·재기동
```

**데모를 처음 상태로 되돌리기**
```bash
scripts/seed.sh           # 서비스 중지 → 초기화 → 성공 시 재기동
# 또는 완전 초기화:
scripts/stop.sh --volumes && scripts/start.sh
```

**커밋 전 점검(로컬 CI 흉내)**
```bash
scripts/test.sh           # 150 + 3 + bandit 0 + audit 0 확인
```

**문제 발생 시**
```bash
scripts/status.sh         # 상태 확인
scripts/logs.sh           # 로그 확인
```

## 8. 트러블슈팅

| 증상 | 원인 · 해결 |
|---|---|
| `Docker 데몬이 실행 중이 아닙니다` | Docker Desktop을 켜세요. |
| `start.sh`가 헬스체크 실패 | `scripts/logs.sh`로 로그 확인. 포트 5000 충돌이면 기존 프로세스를 종료. |
| 포트 5000 사용 중 | `lsof -i :5000`로 점유 프로세스 확인 후 종료, 또는 기존 컨테이너 `scripts/stop.sh`. |
| 브라우저 로그인이 안 됨 | `.env`에 `COOKIE_SECURE=1`이 켜져 있으면 로컬 HTTP에서 브라우저에 따라 쿠키가 막힐 수 있습니다. 주석 처리 후 `restart.sh`. |
| 재시드했는데 로그인 실패 | 재시드는 비밀번호도 초기화합니다. 데모 계정(`admin/admin123`)으로 로그인하세요. |
| `test.sh`가 node 부족으로 실패 | 호스트에 Node 24+ 설치 후 다시 실행. 전체 검증에서는 프론트를 생략하지 않습니다. |
| 시크릿 변경 후 기존 정보 복호화 실패 | 기존 `DATA_KEY`를 복구하세요. 새 키 생성은 기존 암호문의 마이그레이션이 아닙니다. |
| 데이터를 완전히 지우고 싶음 | `scripts/stop.sh --volumes` (되돌릴 수 없음). |
