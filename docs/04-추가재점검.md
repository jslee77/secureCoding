인젝션 차단과 기본적인 객체 권한 검사는 잘 반영돼 있다. 그러나 **안전한 구현의 완성된 레퍼런스로 사용하기에는 추가 수정이 필요하다.** 비밀번호 복구·공유 권한의 상태 전이, 로그인 CSRF, 입력 타입 검증에 실제 결함이 남아 있다. 기존 결과 보고서의 “코드 결함 없음”, “운영 인프라 선택 사항만 남음”은 이번 검증 결과와 일치하지 않는다.

추가 확인 항목은 **높음 2건, 중간 7건, 낮음 2건**이다. 심각도는 본 프로젝트의 기능·공격 전제·영향을 바탕으로 한 검토자의 판단이며 CVSS 점수가 아니다. 낮음 항목은 즉시 침해가 확인된 취약점과 구분한 방어 보완 사항이다. 재설정 기능은 현재 발송 연동이 미구현이므로 정상 사용자에게 전달되는 유효 토큰을 확보한다는 조건을 명시했다.

### S-01. 비밀번호 변경이 기존 재설정 토큰을 무효화하지 않음

**근거:** `app/profile.py:33–36, 74–90, 133–141` ([코드](../app/profile.py)). `_set_password()`는 비밀번호와 JWT 세대만 변경한다. 재설정 테이블은 `/reset-confirm` 성공 경로에서만 소진된다.

**재현:** Alice의 재설정 토큰을 발급 → 현재 비밀번호를 확인하는 정상 변경 API로 비밀번호 변경 → 이전 토큰으로 재설정 → 그 비밀번호로 로그인. 세 요청 모두 `200`이다.

**영향과 전제:** 기존의 미사용 토큰을 확보한 사람은 사용자가 비밀번호를 바꾼 뒤에도 만료 전까지 계정을 다시 장악할 수 있다. JWT 일괄 폐기만으로 복구 수단까지 폐기되지 않는다. 현재 `deliver_reset_token()`은 발송하지 않으므로 외부에서 토큰을 얻는 경로 자체를 발견한 것은 아니다. 테스트는 전달 함수를 가로채 정상 발급 토큰을 확보했다.

**수정:** 모든 비밀번호 변경 경로에서 비밀번호·JWT 세대·미사용 재설정 토큰 폐기를 하나의 트랜잭션으로 갱신한다. 또는 발급 당시 비밀번호 세대를 토큰에 연결하고 확인 시 현재 세대와 비교한다.

**완료 기준:** 발급 → 일반 비밀번호 변경 → 이전 토큰 사용이 `400`이고 새 비밀번호는 유지된다. 변경 전 JWT도 `401`이어야 한다.

### S-02. 재설정 토큰의 일회성 처리가 원자적이지 않음

**근거:** `app/profile.py:133–141`, `app/db.py:40–46` ([프로필](../app/profile.py), [DB](../app/db.py)). `SELECT used=0` → `UPDATE used=1` → 비밀번호 갱신이 각각 분리돼 있다. `execute()`는 호출마다 커밋한다.

**재현:** 동일한 정상 토큰으로 비밀번호가 다른 두 요청을 보낸다. 두 요청이 미사용 토큰을 조회한 직후 진행하도록 스레드 배리어를 넣었으며, DB 결과나 권한 판정은 조작하지 않았다. 두 요청 모두 `200`이다. 기존 테스트는 순차 재사용만 검사하므로 이 조건을 잡지 못한다.

**영향과 전제:** 동일 토큰 또는 같은 사용자에게 발급된 복수 유효 토큰을 동시에 사용할 때 마지막 요청이 비밀번호를 덮어쓴다. 피해자와 토큰 보유자가 경합하는 상황에서 단일 사용 보장이 깨진다. 토큰 없이 계정을 재설정하는 취약점은 아니다. 토큰 소진 직후 해싱·DB 갱신에 실패하면 비밀번호는 그대로인데 복구 토큰만 소진되는 실패 경로도 있다.

**수정:** SQLite에서는 쓰기 트랜잭션을 먼저 확보하거나 조건부 토큰 소진의 영향 행 수를 확인하고, 만료·미사용 조건 확인, 다른 토큰 폐기, 비밀번호 변경, 세대 증가를 동일 트랜잭션에서 처리한다. 비싼 해싱과 DB 잠금의 범위도 조정한다.

**완료 기준:** 같은 토큰 및 서로 다른 동일 계정 토큰에 대한 병렬 확인에서 정확히 한 요청만 성공한다. 비밀번호 갱신 실패 시 전체 변경이 롤백된다. 일회용·만료 요구사항은 [OWASP 비밀번호 복구 지침](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)을 참고한다.

### S-03. 문서 편집 권한이 공개 범위 변경 권한까지 포함함

**근거:** `app/documents.py:103–117`, `app/sharing.py:63–65` ([문서](../app/documents.py), [공유](../app/sharing.py)). 공유 API는 소유자만 허용하지만, 문서 수정 API는 편집자에게 `visibility` 변경을 허용한다.

**재현:** Alice의 비공개 문서 #3을 Bob에게 편집 공유 → Carol의 접근은 `404` → Bob이 `{"visibility":"public"}`로 수정하면 `200` → Carol의 조회가 `200`으로 바뀐다. 공개 범위는 인터넷 비로그인 전체가 아니라 **이 애플리케이션의 모든 로그인 사용자**다.

**영향과 전제:** 공유 대상 편집자가 소유자의 문서와 첨부를 다른 사용자에게 공개할 수 있다. 이는 “공유 권한은 소유자만”이라는 기존 정책을 우회한다. 편집자에게 게시 권한까지 주려는 제품 정책이라면 이를 명시해야 하지만, 시큐어코딩 예제에서는 두 권한을 분리하는 편이 적절하다.

**수정:** `visibility`가 변경되는 요청은 소유자 또는 별도의 게시 권한을 요구한다. 제목·본문 편집과 접근 정책 변경을 구별한다. 사용자·자원·행위별 권한을 명시하라는 [OWASP 인가 지침](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)에 맞춰 권한표를 만든다.

**완료 기준:** 편집자의 본문 수정은 성공하지만 공개 변경은 `403`. 거부 후 제3자의 문서·첨부 접근은 계속 차단된다.

### S-04. 기존 공유 권한을 낮추거나 회수할 수 없음

**근거:** `app/sharing.py:38–41, 71–72`, `app/schema.sql:38–45` ([공유](../app/sharing.py), [스키마](../app/schema.sql)). 공유는 항상 `INSERT`하며 `(document_id,user_id)`에 유일성 제약이 없다. `can_edit=1`인 행이 하나라도 남으면 편집할 수 있다. 공유 삭제 API도 없다.

**재현:** Bob에게 `can_edit=true` → 같은 대상에게 `false`로 재공유 → 두 요청이 성공하지만 Bob의 후속 편집도 `200`이다.

**영향:** 소유자가 읽기 전용으로 바꿨다고 생각해도 이전 편집 권한이 계속 남는다. 공유가 종료된 사용자 접근을 문서 단위로 철회할 방법도 없다.

**수정:** 중복 데이터를 정리하고 복합 유일성 제약 + UPSERT로 현재 권한 하나만 유지한다. 소유자에게 공유 조회·수정·삭제를 제공한다. 기존 중복 권한 병합 기준도 명시한다.

**완료 기준:** 편집 → 읽기 변경 후 편집·업로드는 `403`, 조회는 성공한다. 공유 삭제 후 비공개 문서·첨부·댓글 접근은 모두 거부된다.

### S-05. 로그인·가입은 CSRF 보호 대상에서 빠짐

**근거:** `app/auth.py:76–82, 119, 146` ([코드](../app/auth.py)). CSRF 헤더는 이미 유효한 쿠키로 인증된 요청에만 요구한다. 미인증 로그인은 검사를 건너뛰며, `get_json(force=True)`가 `text/plain`도 JSON으로 해석한다.

**재현:** 쿠키 없는 클라이언트로 외부 `Origin`과 `Sec-Fetch-Site: cross-site`를 보내고, `Content-Type: text/plain` 본문에 공격자가 아는 계정의 자격증명을 넣으면 `200`과 세션 쿠키가 발급된다. HTML의 `enctype="text/plain"` 폼이 추가하는 `=` 문자는 JSON의 무시되는 padding 필드에 넣을 수 있다.

**영향과 전제:** 피해자를 공격자 계정으로 로그인시켜 이후 피해자가 입력한 문서·프로필을 공격자가 자기 계정에서 읽는 로그인 CSRF가 가능해지는 서버 조건이다. 피해자가 공격 페이지를 방문해야 하며, 브라우저의 최상위 탐색·쿠키 정책을 포함한 전체 공격은 이번에 실행하지 않았다. 기존 SameSite=Lax는 미인증 요청을 통한 새 세션 발급까지 막아주지 않는다.

**수정:** 로그인·가입 등 세션을 만드는 요청에도 CSRF 보호를 적용한다. JSON API는 맞는 Content-Type을 강제하고 커스텀 헤더·Origin/Fetch Metadata 정책을 일관되게 사용한다. 파일 업로드까지 일괄 JSON으로 제한하지는 않는다. [OWASP CSRF 지침](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)은 로그인 CSRF와 `text/plain`을 수락하는 JSON API를 별도로 다룬다.

**완료 기준:** 교차 출처 폼 로그인·가입 거부, 정상 프론트 로그인 성공, 쿠키를 사용하는 상태 변경 거부 테스트 유지, 의도한 Bearer API 사용 유지.

### S-06. 입력 검증이 일부 값 허용목록에 한정됨

**근거:** `app/auth.py:119–130,146–155`, `app/profile.py:126–134`, `app/sharing.py:72`, `app/utils.py:41–46`.

**재현:** 로그인에 최상위 배열, 가입 username에 배열, 로그인 password에 객체, 재설정 token에 배열을 보내면 모두 `500`이다. 공유의 `can_edit`에 JSON boolean `false` 대신 문자열 `"false"`를 보내면 참으로 취급해 편집 권한이 생긴다. 공유 요청 자체에는 소유자 인증이 필요하므로 익명 권한 상승은 아니다.

**영향:** 잘못된 데이터가 내부 예외·로그를 발생시키며, 클라이언트의 타입 실수가 과도한 권한 부여로 이어진다. 전역 500 핸들러는 내부 정보 노출을 막지만 올바른 입력 검증을 대신하지 않는다. 주민번호도 형식 검증 없이 저장·마스킹하므로 `-` 앞에 원문을 모두 넣으면 해당 접두부가 그대로 반환될 수 있다(`app/profile.py:43–46,66–70`).

**수정:** 공통 입력 스키마에서 JSON 객체 여부, 각 필드 타입, null 허용, 필수 여부, 길이·형식을 검증한다. `can_edit`는 엄격한 boolean으로 받는다. 주민번호는 필요한 수집인지 먼저 정하고, 유지한다면 정규화·검증 후 고정 형식으로 마스킹한다.

**완료 기준:** 잘못된 타입·null·배열·과도한 길이·문자열 boolean은 의도한 `400/422`이며 DB 변경이 없다. 500을 400으로 바꾸는 예외 처리만 추가하는 것은 불충분하다.

### S-07. 비밀번호 확인과 자원 사용에 대한 남용 제한 부족

**근거:** `app/profile.py:74–87`, `app/__init__.py:83–85`, `app/documents.py:19–39,51–54`, `app/tools.py:28–54,140–164`, `app/files.py:24–50`. 로그인·가입·재설정·자가채점 이외에는 제한이 없다.

**재현:** 로그인된 같은 계정에서 `/api/profile/password`에 틀린 현재 비밀번호를 35회 보내도 전부 `403`이며 `429`가 없다. 1MiB 문서 본문 저장도 `200`이다. 후자는 그 자체로 취약점이 아니라, 계정별 총량·호출량 제한이 없다는 정적 확인의 보조 증거다. 전역 요청 한도 16MiB는 존재한다.

**영향과 전제:** 유효 세션을 확보한 사람은 로그인 API의 제한을 우회해 현재 비밀번호를 계속 추측할 수 있다. 일반 가입 사용자도 대형 문서·업로드·댓글 반복, 검색 전체 본문 응답, PDF 변환·URL 미리보기로 저장소와 워커를 소모할 수 있다. 실제 서비스 거부 성립에 필요한 요청량은 측정하지 않았다.

**수정:** 비밀번호 확인은 계정+IP 기반 제한과 보안 이벤트 기록을 적용한다. 문서·댓글·파일은 필드 크기, 개수, 계정별 저장 총량, 호출량 제한을 둔다. 목록·검색은 페이지네이션한다. 변환 작업은 별도 실행 자원·동시성 제한을 둔다. 기본 Docker는 워커 2개인데 카운터는 memory 저장소라 워커별로 분리된다. 다중 워커에서는 공유 저장소가 필요하다. [Flask 보안 문서](https://flask.palletsprojects.com/en/stable/web-security/)의 자원 사용 제한 설명도 참고한다.

**완료 기준:** 기준 횟수 뒤 비밀번호 확인에 `429`, 사용자별 파일·문서 총량 상한, 제한된 검색 응답, 다중 워커에서도 동일 한도 적용.

### S-08. 문서 삭제가 관련 데이터와 파일을 삭제하지 않음

**근거:** `app/documents.py:131`, `app/schema.sql:28–55`, `app/db.py:18–22` ([문서](../app/documents.py), [스키마](../app/schema.sql), [DB](../app/db.py)). 부모 문서만 삭제한다. SQLite 연결에 `PRAGMA foreign_keys=ON`도 없고 참조 정의에 삭제 연쇄 규칙도 없다.

**재현:** #3에 파일 업로드 → 문서 삭제 `200` → `attachments` 1행, `shares` 1행, 실제 파일 1개가 남는다. 댓글도 코드상 같은 구조다.

**영향:** 사용자가 삭제한 첨부 내용이 계속 디스크·백업에 남고 저장공간도 회수되지 않는다. 현재 다운로드 API는 삭제된 부모 문서에 대한 접근을 거부하므로 **삭제 후 외부 다운로드가 된다는 의미는 아니다.**

**수정:** 관련 DB 행을 트랜잭션으로 삭제하고 외래키·적절한 cascade를 설정한다. 파일 삭제는 실패를 기록하고 재시도 가능한 작업으로 관리한다. 소프트 삭제라면 보관기간과 실제 파기 동작을 명시한다. 업로드 파일 저장 뒤 DB 기록 실패 시 고아 파일 정리도 포함한다.

**완료 기준:** 문서 삭제 후 관련 행·파일 처리 정책이 모두 충족되고, 중간 실패 후에도 정리 작업이 재시도된다.

### S-09. 키 파일 손상을 새 키 생성으로 덮어씀

**근거:** `app/config.py:34–59` ([코드](../app/config.py)). 기존 파일 읽기·JSON 해석의 모든 예외를 빈 저장소로 바꾸고 새 키를 생성해 `w` 모드로 덮어쓴다.

**재현:** 별도 임시 키 저장소를 손상 JSON으로 만들고 환경변수 키가 없는 조건에서 로더를 실행하면 오류 없이 새 키 파일로 교체된다.

**영향과 전제:** 파일 손상·읽기 실패가 최초 설치처럼 처리돼 기존 개인정보의 복호화 키를 잃고 모든 세션 서명 키가 바뀔 수 있다. 키 백업이 없다면 기존 암호문 복구가 불가능하다. 파일 저장형 키를 사용하는 배포에 해당하며, 외부 공격자가 파일을 손상할 수 있다는 경로까지 입증한 것은 아니다.

**추가 정적 확인:** 새 파일을 일반 권한으로 작성한 뒤 `chmod(0600)`하며 실패를 무시한다. 기존 파일의 권한은 검증하지 않는다. 쓰기가 원자적이지 않고 다중 프로세스 간 잠금도 없다. Docker의 `--preload`는 해당 단일 마스터 내 초기화 경합을 줄이지만 공유 볼륨의 복수 인스턴스까지 보장하지 않는다. 환경변수 JWT 키의 최소 강도 검증도 없다.

**수정:** 파일 부재와 파일 오류를 구분하고 기존 키 저장소 오류에는 명시적으로 시작을 중단한다. 최초 생성은 제한된 권한·배타적 생성/잠금·원자적 기록으로 처리한다. 키 형식·JWT 키 강도를 검증하며 회전·백업·복구 절차를 둔다.

**완료 기준:** 손상·권한 오류에서 키를 덮어쓰지 않고 기동 실패, 동시 최초 기동 시 동일 키, 생성 즉시 제한된 파일 권한.

### S-10. 민감 응답과 로그아웃 화면의 잔류 방지 부족

**근거:** `app/__init__.py:89–94`, `app/auth.py:105–113`, `app/profile.py:49–58`, `app/files.py:75`, `static/app.js:50–55`.

**재현:** 프로필 응답에 `Cache-Control`과 `Vary`가 없으며 파일 응답은 `no-cache`다. `no-cache`는 저장 금지가 아니라 재사용 전 검증을 뜻한다. 실제 공유 캐시를 통한 다른 사용자 정보 획득은 검증하지 않았다.

**보완:** JWT·개인정보·비공개 문서·첨부 응답은 `Cache-Control: no-store`로 정책을 명시한다. 정적 자원까지 일괄 저장 금지할 필요는 없다. 로그아웃 시 현재 프론트는 화면을 숨길 뿐 문서·프로필·관리자 DOM을 지우지 않으므로 민감 화면·메모리 상태도 초기화한다. 다음 사용자에게 이전 화면이 순간적으로 노출되지 않는지 브라우저 테스트를 추가한다. [OWASP 세션 관리 지침](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)을 참고한다.

### S-11. 파일 확장자와 실제 내용의 일치 검증이 없음

**근거:** `app/files.py:38–46`, `app/utils.py:91–94` ([파일](../app/files.py), [유틸](../app/utils.py)). 업로드 허용 여부를 확장자로만 판단한다.

**재현:** 내용은 `not an image`인 `fake.jpg`가 `200`으로 저장된다.

**영향의 한계:** 무작위 파일명, 정적 경로 밖 저장, 다운로드 권한 검사, attachment, nosniff는 이미 적용돼 있다. 따라서 이 관찰만으로 서버 RCE·저장형 XSS라고 평가하지 않는다. 허용된 형식만 받는다는 정책과 실제 저장 내용의 불일치, 수신자에게 위험 파일을 전달할 가능성이 남는다.

**보완:** MIME 헤더를 신뢰하는 데 그치지 말고 파일 시그니처와 안전한 파서로 형식을 검증한다. 이미지라면 크기·픽셀 수 한도와 재인코딩을 고려하고, PDF 등은 사용 목적에 맞는 검사·격리 정책을 둔다. 악성코드 검사 필요성은 배포 위험도에 맞춰 정한다. [OWASP 파일 업로드 지침](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)을 참고한다.

## 레퍼런스로 남기기 전에 함께 정리할 항목

아래는 위 11건에 중복 집계하지 않은 운영·명세·추가 검증 항목이다.

1. **기본 데모 노출 범위:** Compose의 `5000:5000`은 루프백 한정이 아니다. 공개된 관리자 비밀번호로 시드하는 로컬 예제는 `127.0.0.1:5000:5000`을 기본으로 두고, 운영 예제는 별도로 제공하는 것이 안전하다. 방화벽·호스트 배포 상태는 이번에 확인하지 않았다. 이미 시드된 볼륨은 `SEED_DEMO_DATA`만 제거해도 계정이 지워지지 않는다.
2. **교육용 잔재:** 플래그 API 외에도 `app/sharing.py:105`의 `/api/admin/secret`, `app/tools.py:168`의 메타데이터, seed의 고정 가짜 시크릿이 남아 있다. 현재 관리자로 제한된 예제 값이며 실제 인프라 비밀 유출이라고 단정하지 않는다. 운영 프로파일에서 명시적으로 제외한다.
3. **업그레이드 검증:** `ensure_schema()`는 컬럼·테이블만 추가한다. 구버전 `static/uploads` 파일 이동, 기존 개인정보 암호문 변환·키 회전은 처리하지 않는다. 특히 로컬 구버전 파일이 그대로 있다면 정적 라우트가 제공할 수 있다. 현재 잔류 파일 유무를 확인한 결과는 아니며, 구버전 데이터로 마이그레이션 테스트가 필요하다. DB 키와 암호문을 동시에 보존·변환해야 한다.
4. **인증 수단의 의미:** `api_token`은 DB에 원문으로 저장되지만 실제 요청 인증 경로는 JWT뿐이다. 현재 API 토큰 인증 취약점으로 집계하지 않는다. 기능을 제거하거나, 도입할 때 해시 저장·범위·만료·폐기를 설계한다. JWT refresh도 확인·폐기·발급이 분리돼 있으므로 일회성 회전을 의도한다면 병렬 refresh를 추가 검증한다.
5. **운영 보장:** HTTPS 리다이렉트, 신뢰 프록시에서만 접근 허용, 운영 Secure 쿠키 강제, 로그 회전·감사 로그, 시크릿 복구, 백업·파기 정책을 문서화한다. 현재 `Secure`는 `request.is_secure`에 의존한다. 로그인 제한은 IP 기반뿐이므로 다중 IP에 걸친 계정별 추측도 별도로 고려한다.
6. **의존성 재현성:** 직접 의존성은 고정돼 있지만 전이 의존성 잠금·해시, Python 이미지 digest, Actions commit pin은 없다. 현재 감사 결과는 기록한 해석 결과에 한정된다. 레퍼런스의 재현성을 위해 잠금과 정기 갱신을 함께 제공한다.
7. **기능 정확성:** 재설정 발송과 실제 PDF 변환기는 미구현/미설치다. 공유받은 문서는 상세 접근이 가능하지만 목록·검색에서는 제외된다. `run.py`는 앱 생성이 이미 DB를 만든 뒤 존재 여부를 검사하므로 주석의 자동 seed가 동작하지 않는다. 보안 취약점과 구분해 명세·문서를 정리한다.

## 유지할 만한 구현과 검증 공백

SQL 파라미터 바인딩, 동적 SQL 식별자 허용목록, 고정 템플릿 값 주입, 셸 미사용, JSON 전용 백업, argon2id 해싱, JWT 알고리즘 제한, DB 기반 관리자 재검증, 문서별 파일 접근통제, 업로드 경로 봉인, SSRF 호스트·포트 허용목록과 IP 고정, CSP와 프론트 출력 이스케이프는 유용한 레퍼런스다. 이번 검토 범위에서 이 주요 경로의 신규 SQLi·SSTI·명령 주입·임의 파일 읽기 우회는 확인하지 않았다.

현재 85개 테스트는 단일 요청의 차단과 순차 세션 전이에 집중돼 있다. 다음 검증이 추가돼야 한다.

- 인증: 병렬 재설정/refresh, 일반 비밀번호 변경과 재설정 토큰의 관계, 로그인 CSRF, 비밀번호 확인 레이트리밋.
- 인가: 소유자·편집자·읽기 사용자·비공유 사용자별 공개 변경, 공유 강등·철회, 첨부와 우회 접근 경로.
- 입력: 최상위 JSON 타입, 필드 타입·null·길이, boolean 엄격성, 실제 업로드 형식.
- 데이터: 부모 삭제와 파일 정리, 업로드 실패 롤백, 구버전 데이터 마이그레이션, 손상·경합 키 저장소.
- 운영: 실제 Python 3.12 이미지, 다중 워커 레이트리밋, HTTPS/프록시, 브라우저 CSRF·로그아웃 잔류, 실제 변환기·네트워크의 제한.

## 수정 후 재검증

S-01~S-11은 현재 코드에서 조치됐으며 Python 3.12 회귀 테스트 131개와 프론트 테스트 3개가 통과했다. 자세한 변경·검증·운영 한계는 [최신 결과 보고서](03-결과보고서.md)에 있다. 위의 추가 검토 항목 중 외부 발송·TLS/Redis·실제 변환기·공급망 잠금 등 운영 과제는 결과 보고서 5장에 별도로 남겼다.

```bash
python -m pytest -q
node --test tests/frontend.test.cjs
python docs/security-review/probe_security.py
bandit -r app/
```

검증 실행기는 임시 DB·키·파일을 사용하는 pytest를 실행하며 실패하면 비정상 종료한다. 과거의 취약 응답을 기대하는 스크립트가 아니다. 수정 전 근거는 observations-before.jsonl과 dependency-audit-before.json에 보존했다.
